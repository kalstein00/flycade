# 5분 학습 구간과 추락 판정 수정

사용자 요청: 정체·사망과 점프 해제/재입력·화면별 행동을 진단하고, 학습은5분 단위로 수행한다. 실패를 숨기지 않고 결과로 다음 설정을 판단한다. 반복적인 에이전트 폴링 대신 완료 시 `codex queue`로 이어간다.

## 재현과 발견

[구조화된 진단](fall-diagnosis.json). reward-v2-001의 최종 평가3개 에피소드 행동을 실제 NES에서 재생했다. 모든 전이의 최대 전진 거리와 종료 사유가 원본과 일치했다. 진단 스크립트는 `reports/reward-v2-001/diagnosis`에 결과를 남겼고, 해당 실행 소스/lock을 `reports/reward-v2-001/source`에 보존했다.

- seed11: 파이프 앞에서 정체. 점프 버튼을44번 해제했으며 최대 연속 유지52프레임. 버튼을 전혀 해제하지 않는 고장은 아니다. 마지막 지상 구간에서는 A를 계속 눌러 재점프가 지연된 사례가 있다.
- seed22: 파이프를 넘은 후 적과 충돌해 사망. 점프 해제21회, 최대 유지36프레임.
- seed33: 낭떠러지 추락. 1012프레임에 `player_y_high=2`가 됐지만 환경은1268프레임까지 사망 판정을 미뤘다. 복귀 불가능한256프레임(60fps 기준4.27초) 동안 전이가 계속됐고 화면 밖 이동도 전진 거리/보상에 포함됐다.
- 실제 화면별 행동4 확률의 범위 차이는 에피소드별 약8.3~9.8%p였다. 화면 입력을 완전히 무시하는 정책은 아니지만, 이 수치만으로 유용한 장애물 인식을 배웠다고 판단하지 않는다.

[파이프 정체](fall-screens/episode-0.png), [파이프 위 점프](fall-screens/episode-1.png), [추락 후 화면](fall-screens/episode-2.png). 이미지와 RAM/전이 기록을 함께 확인했으며 마지막 화면의 적을 플레이어로 혼동하지 않는다.

원인 후보는 버튼 해제 부족, 화면에 둔감한 정책, 사망 신호 지연이었다. 직접 재현된 사망 신호 지연부터 수정한다. 자동 점프나 특정 버튼 강제 선택은 추가하지 않는다.

## 수정과 검증

지원하는 World1-1에서 플레이어가 화면 아래로 떨어지는 `player_y_high>=2`를 death terminal로 처리한다. 이 행동 집합에는 DOWN이 없어 수직 파이프 진입이 없고, 구름 보너스 출구도 지원 범위 밖이다. 게임 상태 범위 확인 이후에 적용하며 완주·게임 시간 초과 판정의 우선순위는 유지한다. 화면 위로 올라간 high0은 사망이 아니다.

[SMB의 PlayerHole 루틴](https://github.com/pgattic/smb1-disasm/blob/master/engine/game-mode/routine/player-control.asm)은 high2부터 낭떠러지 처리를 시작하고, 음악/더 아래 위치를 기다린 뒤 lose-life 루틴으로 이동한다. 기존 환경은 마지막 engine/lives 변화만 기다렸다.

환경 경계의 회귀 테스트가 기존 코드에서 실패함을 확인한 뒤 수정했다. 실제 NES의 저장된 추락 입력(`docs/validation/fall-actions.json`)은1012프레임에서 즉시 death로 종료되고, 이전1211px의 화면 밖 추가 거리를 인정하지 않는다. 기존 완주1361프레임과 적 처치2회, high0 점프 보호를 포함해 관련10개 테스트를 통과했다.

보상 계수·모델·학습률·탐색 설정은 reward-v2와 동일하게 두고 종료 판정만 수정한다. 환경 코드 호환성 때문에 이번 첫 구간은 새 Run으로 시작한다. 그 이후에는 같은 Run의 checkpoint·optimizer·누적 진도를 이어간다. 옛 평가와의 거리 직접 비교에는 판정 변경의 영향이 있으므로 새 Run 안에서 동일 프로토콜의 초기/구간 시작/최종 평가를 비교한다.

## 실행

새 Run(기본300초):

```bash
uv run --offline --locked --extra graph --extra train python scripts/reward_trial.py \
  --output reports/five-minute-001 --queue-thread "$CODEX_THREAD_ID"
```

같은 학습의 다음5분:

```bash
uv run --offline --locked --extra graph --extra train python scripts/reward_trial.py \
  --resume-run reports/five-minute-001/run --output reports/five-minute-002 \
  --queue-thread "$CODEX_THREAD_ID"
```

각 구간 출력은 새 디렉터리에 기록하고 원래 Run은 유지한다. `starting_catalog`에 시작 전 평가를 보존한다. 300초는 재개 시작부터의 세션 벽시계이며 주기 평가/준비 시간을 포함하고 안전 저장에는 약간의 추가 시간이 필요하다. 실제 학습 시간은 별도 기록한다. 초기 평가와 첫1 update 준비 시간은 세션에 포함되지 않는다. 이후 구간에서는 초기화를 다시 하지 않는다.

실제 Windows 화면과 WSL 재시작 인수는 #17의 별도 미완료 항목으로 유지한다. 5분 성과 확인을1시간 안정성 인수로 대체하거나, 그 반대로 대체하지 않는다.

진단 재현 명령(수정 전 소스와 정책을 고정):

```bash
PYTHONPATH="$PWD/reports/reward-v2-001/source/src" .venv/bin/python \
  reports/reward-v2-001/diagnosis/reproduce.py
```

Standards 리뷰: hard0, heuristic0. Spec 리뷰: 지적0. 관련 환경/실제NES10개, 구간CLI3개 통과, mypy38개 소스 통과. 전체 회귀115개(51/40/24)가327.08초에 모두 통과했다. 실제5분 성과는 아래에 기록한다.

## 첫5분 결과

[구조화된 근거](five-minute-001-evidence.json). Run `reports/five-minute-001/run`, 벽시계302.63초, 실제 학습295.96초. 준비1 update에서307 updates까지 진행하고 정상 저장했다. nonfinite0, 환경 종료, 잔류 worker0, 영상 기록 완료다. 이번 결과 분석에서 추가 구간은 시작하지 않았다.

| 동일 평가 seed11/22/33 | 거리(px) | 평균(px) | 완주 | 사망 | 정체 |
|---|---|---:|---:|---:|---:|
| 시작 전 초기 정책 | 682 /555 /250 | 495.67 | 0/3 | 1 | 2 |
| 중간250 updates | 564 /556 /684 | 601.33 | 0/3 | 0 | 3 |
| 최종307 updates | 629 /682 /268 | 526.33 | 0/3 | 2 | 1 |

최종 평균은 초기 대비30.67px(+6.19%) 증가했지만, 중간 평가보다75px 낮아졌다. 세 seed 중 하나는 초기보다 후퇴했다. 완료·생존 개선이 없고 표본도3회이므로 안정적인 학습 개선을 확인했다고 결론내리지 않는다. 추락 종료가 늦던 오류는 별도 회귀 검사로 수정이 입증됐으나, 그것이 이번 짧은 학습의 성능 향상을 보장하지 않는다.

마지막128회 행동0~6은13 /6 /25 /55 /8 /17 /4회였다. 최빈 행동은 RIGHT+B(55회,42.97%), RIGHT+B+A는8회(6.25%)다. 평균 행동 확률은6.11 /7.20 /16.46 /43.57 /3.58 /19.88 /3.20%, rollout entropy1.565nats로 완전 고정은 나타나지 않았다. 다양성이 있다는 사실 자체를 상황에 맞는 행동 능력으로 해석하지 않는다.

학습 중 종료245회는 사망157·정체88회였다. 적 처치192회가 감지됐으나 초기와 동일 조건의 처치 수 비교가 없어 처치 능력 향상으로 보고하지 않는다. 누적 보상은 전진+1441.63, 적 처치+96, 사망−1570, 정체 종료−880, 정체 시간−166.785, 활성 시간−156.575, 완주0이다. 총보상은 에피소드 수와 판정 변경의 영향을 받으므로 구형 Run과 직접 비교하지 않는다.

다음 판단에는 중간250과 최종307 정책의 정체·사망 장면을 비교하는 것이 유용하다. 같은3회 평가를 보고 즉시 보상 숫자를 또 바꾸거나1시간으로 연장하지 않는다. 다음 구간을 진행할 경우 같은 Run에서5분씩 재개하고 `starting_catalog`의 직전 평가와 비교한다. 실제 Windows 화면·WSL 재시작 인수는 여전히 미확인이다.


## 추가 확인: 23회 정책 비교

[전체 원자료](five-minute-comparison/evidence.json), [재현 스크립트](five-minute-comparison/check.py). 학습 없이 저장된 초기·250·307 updates 정책을 실제 NES에서 각각23회 평가했다. 기존 seed11/22/33의 거리9개가 모두 원본과 정확히 일치했다. 추가 seed101~120은 같은 World1-1에서 행동 추출 난수만 바꾼다. 새 맵에 대한 일반화 검증은 아니다.

| 정책 | 추가20회 평균 거리(px) | 전체23회 평균 거리(px) | 완주 | 사망 | 정체 |
|---|---:|---:|---:|---:|---:|
| 초기 | 492.65 | 493.04 | 0/23 | 11 | 12 |
| 250 updates | 597.05 | 597.61 | 0/23 | 10 | 13 |
| 307 updates | 610.80 | 599.78 | 0/23 | 8 | 15 |

최종은 초기보다 전체 평균106.74px(+21.65%) 증가했다. 그러나 완주는 없고23회 중15회가 정체다. 기존3회에서 보인 중간 대비 하락은 추가20회에서는 재현되지 않았다. 추가 seed별 중간→최종 비교는 개선10·악화7·동률3회, 평균+13.75px다. 전체 평균은 중간과 최종이 거의 같다. 따라서 정책이 명확히 퇴보했다고도, 지속적으로 좋아지고 있다고도 단정하지 않는다. 동일한 단일 학습 실행에 대한 탐색적 비교이며, 독립 학습 반복이나 통계적 유의성 검증은 아니다.

### 실패 장면과 행동

원본 seed의 마지막50개 전이와 종료 직전 화면을 원자료 폴더에 보존했다. 화면은 해당 행동 직전이며 tail의 position/frame/reason은 행동 이후, y/state는 행동 직전 값이다.

- 중간 seed11/22/33은 파이프 앞 정체로 끝났다. [seed11 화면](five-minute-comparison/update-250-seed-11-step-214.png)에서 파이프 앞 점프를 볼 수 있다.
- 최종 seed11은 파이프 사이의 적과 충돌했다. [충돌 직전](five-minute-comparison/update-307-seed-11-step-158.png).
- 최종 seed22는 파이프를 넘지 못하고 정체했다. [종료 직전](five-minute-comparison/update-307-seed-22-step-193.png).
- 최종 seed33은 초반 적과 충돌했다. [충돌 직전](five-minute-comparison/update-307-seed-33-step-37.png).

점프 해제 횟수는 중간 원본3회에서53/53/57, 최종37/50/7회다. 에피소드 길이가 다르므로 횟수 자체를 개선 척도로 삼지 않는다. 버튼을 전혀 해제하지 않는 고장은 재현되지 않았지만, 적절한 점프 시점과 유지 시간을 배웠다는 의미도 아니다.

23회 평가 전체에서 실제 선택된 행동 비율(0~6)은 초기13.19/12.44/14.87/15.17/14.90/13.87/15.55%, 중간4.92/1.78/20.63/24.60/19.65/8.13/20.29%, 최종7.29/6.28/18.36/42.27/3.66/19.59/2.55%다. 최종의 RIGHT+B 비중이 높아졌고 LEFT가 줄었다. 이는 행동별 전이 수를 합친 비율로 긴 에피소드에 더 큰 가중치가 있다. 방향 편향의 변화와 거리 증가만으로 화면의 적·파이프를 유용하게 인식한다고 결론내릴 수 없다.

### 보존과 다음 판단

평가 전후 initial.pt/final.pt/latest.json의 SHA-256 일치를 검사했다. src/flycade 수정, 보상 변경, 추가 학습은 하지 않았다. 기존3 seed만으로 즉시 보상을 다시 바꾸기보다, 다음 학습을 진행하면 같은 Run을5분 재개하고 동일한 추가20 seed 평가도 비교하는 것이 적절하다. 화면 인식의 기여를 확인하려면 별도로 정상 화면과 통제된 입력의 정책 반응을 비교해야 하며 이번 결과에는 그런 인과 검증이 포함되지 않는다. 실제 Windows 화면과 WSL 재시작은 계속 미확인이다.
