# T09 — 정상본 복구와 보호

저장 공개 순서는 임시 `.partial` 작성→파일 fsync→readback/해시→불변 `.pt` rename→디렉터리 fsync→개별 metadata 원자 공개→`latest.json` 원자 공개/fsync→`*.committed.json` 확인 기록→편의 `final.pt` 링크다. `latest.json`이 권위 있는 공개 지점이다. 다음 저장은 기존 정상본을 수정하지 않는다. 공개 뒤 확인 기록 전 죽은 경우에도 latest를 완전히 검증한 뒤 확인 기록을 보충한다.

복구는 latest를 먼저 검증하고, 실패하면 공개 확인 기록이 있는 이전 후보를 최근 저장 시각 순으로 검증한다. `.partial`, 확인 기록 없이 남은 `.pt`/metadata는 후보가 아니다. 파일 해시만 확인하고 복원하지 않는다. Python/패키지/소스/lock/graph/ROM/state/초기 모델 정체성, 전체 모델·optimizer·RNG·안전 경계와 metadata의 Run/세션/update를 모두 검증한다. 일치하는 후보가 없으면 명확히 실패하며 온라인 데이터나 부분 가중치로 우회하지 않는다.

검증 후 같은 Run의 새 세션을 만든다. `recoveries/<ID>.json`에 거부한 후보와 오류, 선택 checkpoint, 이전/새 세션, 복원 update/전이, 마지막 진도 기록 대비 되돌린 범위를 기록한다. 기존 전이/update 로그는 그대로 유지하고 새 세션 ID로 덧붙인다. 복원한 누적 카운터에서 진행하므로 중복 step을 역사 전체 합계로 더하지 않는다. 게임은 새 에피소드이며 중단 에피소드를 종료/성공으로 집계하지 않는다. 마지막 report와 같은 세션의 로그 끝부분을 확인하지만 아직 기록되지 않은 작업의 손실은 추가로 있을 수 있다.

브라우저는 복구 검증 중·완료·실패, 되돌린 update/전이, 후보별 오류를 표시한다. 정상 후보가 없을 때는 과거 저장 시각을 현재 복구 가능한 정상본처럼 표시하지 않는다. CLI 결과의 `recovery`와 `status`의 복구 상태도 같은 사건을 읽는다.

## 보존

기본 최근 정상본3개(`TrainingConfig.keep_checkpoints`)를 보존한다. 사용자 pin과 최고본 참조는 개수 제한에 추가로 보호한다. 초기 정책/초기 snapshot, 그래프와 ROM 참조는 이 단계에서 삭제하지 않는다. 보호되지 않은 오래된 정상본만 새 저장 완료 뒤 제거하며 복구 확인 기록부터 제거해 삭제 중단으로 불완전한 후보가 생기지 않게 한다. 손상 파일은 진단용으로 보존한다. 정책 snapshot·영상·그래프 전체 공간 관리는 #16에서 다룬다.

```bash
uv run --offline --locked --extra train flycade checkpoints reports/my-run
uv run --offline --locked --extra train flycade pin-checkpoint reports/my-run <checkpoint-UUID>
uv run --offline --locked --extra train flycade pin-checkpoint reports/my-run <checkpoint-UUID> --remove
uv run --offline --locked --extra train flycade resume reports/my-run
```

pin 변경은 writer 점유 중 거부하며 저장 후 종료한 상태에서 수행한다. `checkpoint-references.json`의 `pins`와 `best` UUID 배열이 공통 보호 계약이다. #13의 최고 평가본은 이 계약을 사용한다. `checkpoints`의 `integrity_valid`는 metadata/파일 무결성이며 현재 실행 환경에서의 전체 resume 가능성을 미리 보장하지 않는다.

## 장애 검증 경계

CLI/artifact 공개 경계에서 실제 프로세스를 실행한다. 테스트용 C 라이브러리는 `LD_PRELOAD`로 해당 임시 Run의 POSIX write에 ENOSPC, fsync와 latest rename에 EIO를 주입한다. 실제 디스크를 가득 채우거나 앱 내부 저장 함수를 교체하지 않는다. 실행에는 로컬 C compiler(`cc`)가 필요하다. 임시 라이브러리는 pytest 임시 디렉터리에만 생성한다.

inotify의 임시 파일 생성·데이터 rename·latest 공개 알림에 SIGKILL을 주입한다. 알림은 비동기이므로 정확히 syscall 사이에서 멈췄다고 주장하지 않는다. 결과 포인터는 이전 또는 새 완전 정상본 중 하나여야 하며, 새 프로세스의 추가 학습·카운터·writer 해제와 이전 인코더 실행 종료를 검사한다. 전원 차단이나 실제 PC 재시작은 이 프로세스 장애 검사의 대체 대상이 아니며 #17에서 확인한다.

## 실제 NES/5090 복구

전용 검증 Run `reports/t09-recovery-001`, Run UUID `f3ae6776-1873-44c2-ac44-433b3f79481d`를 실제 graph/초기 평가로 생성했다. update4→8→12를 저장한 뒤 최신 전체 checkpoint만 의도적으로 손상시켰다. update8/256전이 정상본을 검증해 같은 Run의 새 세션으로 복구하고 update12/384전이까지 추가 학습했다. 되돌린 범위는4updates/128전이이며 기존 사건/전이 로그를 보존했다. [기계 판독 증거](T09-evidence.json)에 후보 해시·거부 사유·두 세션·복구 사건을 기록했다.

실제 로컬 HTTP와 Chromium에서 후보 오류를 펼쳐 확인했다. [1280 화면](t09-screens/recovery-1280.png), [1920 화면](t09-screens/recovery-1920.png), [390 화면](t09-screens/recovery-390.png)은 같은 실제 Run이며 가로 넘침이 없다. detector의 이미지 src 경고는 JS가 실제 원본 픽셀을 주입하는 비활성 template로 실제 화면에서 정상 표시된다. 이 검증은 사용자 기존 Run을 손상시킨 것이 아니며 실제 PC 재부팅을 수행한 것도 아니다.
