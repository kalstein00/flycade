# A5 — 실측 실행 프리셋과 자원 예산

## 재현 절차

ROM·실제 graph 준비와 Chromium 설치를 마친 환경에서 다음 두 명령을 별도 터미널에서 실행한다. 측정 디렉터리는 새 경로여야 한다. 기본은 **각 150초의 네 구간**, 최소 600초의 정상 학습 측정이며 준비·초기 평가·저장·재개·평가 시간은 추가된다.

```bash
uv run --offline --locked --extra graph --extra train python scripts/measure_resources.py \
  --graph .flycade/graphs/visual-a2-final-001 --output reports/a5 --phase-seconds 150
uv run --offline --locked --extra graph --extra train python scripts/measure_save_latency.py reports/a5
```

측정 순서는 관찰 off → GUI on → GUI+동시 CPU 평가 → CPU 순차 평가 후 GUI+학습이다. 같은 Run의 각 구간을 SIGINT 안전 저장으로 종료하고 다음 구간은 새 프로세스 `resume`으로 시작한다. 초기 평가를 본 학습 전에 남기고 동시/순차 평가 모두 직전의 고정 snapshot을 사용한다. 초기 평가·복원·브라우저 초기화 대기에도 별도 sampler가 계속 표본을 수집한다. 각 구간의 지표와 관찰용 PNG, stdout/stderr, checkpoint, 전체 `/proc` 표본을 로컬 측정 디렉터리에 보관한다.

`--fixture --phase-seconds 1`은 공개 경로의 CPU 회귀검사용이다. 해당 보고서는 실제 장비 증거 및 A5 시간 조건 충족으로 표시하지 않는다. 반복 측정은 다른 디렉터리에서 수행한다. 종료되지 않는 CLI에는 제한 시간 이후 정리 절차를 적용하며 오류 시 로그를 보존한다.

## 측정의 의미

- 프로세스 트리 RSS/swap: 실행기·trainer·ffmpeg·별도 evaluator·로컬 서버·Chromium 및 자식 프로세스의 `/proc` 표본 합계다. shared page가 중복 계산될 수 있는 보수적 RSS 합계이며 peak PSS는 아니다. 표본 간 짧은 peak는 놓칠 수 있다.
- trainer의 `ru_maxrss`와 PyTorch peak CUDA allocated는 별도로 기록한다. 전체 GPU 사용량은 nvidia-smi의 시스템 값으로 기록하여 Windows/다른 GPU 작업 사용량까지 포함한다.
- paging은 시스템 pswpin/pswpout 차이, 프로세스별 VmSwap와 major fault를 기록한다. major fault에는 최초 파일 page-in도 포함되므로 이를 swap과 같다고 해석하지 않는다.
- update 시간은 완료된 update 로그의 학습 누적 시간 차이다. 저장·종료 지연은 SIGINT 요청부터 프로세스 종료까지의 안전 경계 대기·체크포인트·인코더 종료를 포함한다. 별도 watcher는 첫 저장 요청 이전에 시작해야 하며 지연 시작은 거부한다. stderr 요청 알림→원자적 정상본 공개→완료 출력의 50ms 표본 관측값을 기록한다. 시스템 부하 때문에 실제 관측 오차는 poll 주기보다 클 수 있다.
- 전처리는 재사용된 graph artifact의 measurement.json에 별도 기록한다. 10분 비용에 다운로드/최초 데이터 전처리를 합산하지 않는다.

## 프리셋 구성과 실험 사전 조건

프리셋은 `configs/preset-small.json`, PPO 설정은 `configs/training-small.json`, 평가 조건은 `configs/evaluation-small.json`으로 분리한다. 실제 FlyWire v783.0 graph 4,622노드/8,010 연결, 상태 차원8·전파2회, 환경1개, rollout=batch32, PPO2 epochs, FP32, 3Hz/128노드/512연결 표시를 사용한다. graph 자체의 SHA를 고정한다. 전체 뇌나 임의 CNN 성공으로 이 경로를 대체하지 않는다.

초기 모델부터 총100,000 updates(3,200,000환경 전이)를 계획하고, 완료율 우선→평균 진행 거리 보조→동률 기존본 유지로 최고본을 선택한다. 평가 seed11/22/33·확률적 행동·에피소드당 최대1,800 emulator frames·첫15초 영상, 매1,000 updates의 순차 CPU 평가를 채택한다. 평가 주기 실행 기능은 #13에서 이 설정을 적용한다. 수집시간 추정은 전이 처리량으로 계산하며 게임 클리어 예상시간이 아니다.

기본 관찰은 3Hz이고 필요하면2Hz로 낮춘다. 더 큰 그래프·다중 환경·큰 rollout·CUDA 동시 평가는 이 측정으로 승인하지 않는다. 32 batch의 측정된 메모리 여유를 더 큰 프리셋의 검증으로 확대 해석하지 않는다. 현재 모델은 temporal recurrence/AMP/사전학습/교사를 사용하지 않으며, PPO는 고정 학습률과 full-rollout batch를 사용한다.

요청 관측→정상본 공개는0.050~0.252초, 완료 출력까지0.303~0.405초였다(50ms watcher). 별도1초 poll의 종료 확인 상한은1.001초다. 전체 tree peak RSS **3.40 GiB**, ffmpeg 동명 프로세스 합계 peak146.22 MiB, Chromium538.50 MiB, Playwright MainThread128.45 MiB였다. trainer/evaluator를 합친 python3 이름별 peak는2.78 GiB다. 관찰은 trainer 내부 thread이므로 독립 RSS가 없으며 on/off trainer 차이와 tree 합계를 사용한다. 에뮬레이터 worker는 trainer와 같은 프로세스에 있다. PyTorch peak allocated106.61 MiB, 시스템 GPU 사용 peak3429 MiB, GPU 여유 최소28759 MiB였다. 프로세스 swap0, 시스템 pswpin/out 증가0, 종료 후 자식0, 관찰 전송 폐기0이다.

호스트는 Ryzen7 7800X3D/16논리CPU, Windows31.22 GiB/시작 가용8.08 GiB, WSL 실효한도15.23 GiB/시작 가용12.89 GiB였다. 종료 직전 Windows 가용6.54 GiB를 재확인했다. Windows 가용은 연속 최솟값이 아닌 두 시점 측정이다. SB3 없이 자체 PPO를 사용한다. 코어/integration/ROM/state의 정확한 해시는 증거의 registration을 따른다. 전처리는6.85초/peak RSS2.04 GiB(DuckDB512MB, thread1)로 별도다.

채택하는 **운영 진입/중단 판단 기준**은 tree RSS6 GiB 이하, PyTorch allocated512 MiB 이하, 시스템 GPU 사용8 GiB 이하, 시작 Windows 가용6 GiB 이상·Linux 가용4 GiB 이상, 지속 swap 없음, 처리량80전이/초 이상, update p95 1초 이하, 저장·종료5초 이하이다. WSL 한도15.23 GiB에서 tree 예산은9 GiB 이상 여유를 남기며 시스템 GPU 예산은24 GiB 가까운 여유를 남긴다. 이번 실측은 모두 기준 안이었다. 이는 현재 자동 강제 제한 기능을 뜻하지 않는다. 나머지 앱의 메모리 소비가 커지면 시작을 미루고 관찰2Hz/순차 평가로 낮춘 뒤 재측정한다.

100,000 updates의3.2M전이 수집 추정은 실측124.57전이/초 기준 약7.14시간, 기준선80에서는 약11.11시간이며 평가·저장·재시작 시간은 별도다. 클리어까지 걸리는 시간은 알 수 없다. 이번 자원 실험의100만 update 상한은 강제 종료를 피하는 실험용 값이며 본 학습 예산은 채택 프리셋의10만 updates다.

첫 측정 `t07-a5-001`은 초기 평가/복원 대기의 자원 표본 공백을 리뷰에서 발견해 중단했다. 초기화부터 끝까지 background sampler를 적용한002만 A5 근거로 채택한다. 새 라이브러리 조합 실패는 이번에 관측하지 않았으며 A1~A3의 후보/실패 기록을 유지한다. 더 큰 graph·다중 환경·다른 패키지 조합·1시간 연속/재부팅은 아직 검증하지 않았다.
